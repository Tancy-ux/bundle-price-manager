System design

One single-page React app, two interchangeable back ends that serve the same /api routes, two storage documents, and two outside systems it reads from. Shopify is the only one it ever writes to, and only through the "push price" button.

Key flows

Edit & autosave
Any change in the UI → the client diffs against its last confirmed save → sends only the changed items → server re-reads, merges, writes, keeps a backup → returns the merged doc, which also brings in anyone else's edits. app.src.jsx diffById · lib/mergeData.js
Stock refresh
Every 4h a GitHub Action pulls Shopify inventory and writes stock onto matching products in Redis. The app picks it up on next load. fetch-stock.yml · scripts/fetch-stock.js
Sync button
One Shopify fetch → new products, new bundle shells, stock → one write. 4h cooldown, server-enforced. api/sync.js · server.js · lib/shopifySync.js
Push price
Confirm dialog → PUT to Shopify for that one variant id, price field only → re-read the doc fresh and save the new price with a history entry. api/push-price.js · pushVariantPrice
Zoho refresh
Button (8h cooldown) or 8-hourly Action → fetch items + open POs → merge numbers into the reorder doc, never touching typed dates/notes. api/reorder.js · lib/zohoReorder.js · zoho-reorder.yml
OOS download
Sync (if the 4h cooldown allows) or reload the stored doc → build the Word file in the browser with docx → download. Nothing is sent anywhere. app.src.jsx exportOOS · downloadOOSDocx

Single points to know about

The app needs unpkg to load React (and docx for downloads) — a network that blocks it shows a "Couldn't load the app" message. All catalog data is one Redis value, written whole on each save (merged server-side), which is fine at this size (~740 products) but is the thing to revisit if the catalog grows by an order of magnitude.

The data model

Two documents, kept apart on purpose so a Zoho refresh can never touch the Shopify catalog and the other way round.

Catalog — data/data.json or Redis bundle-manager:data

FieldWhat it is
products[]Flat catalog. Each has id, sku, name, price, active, history, plus stock, stockTracked, stockUpdatedAt once a stock sync has touched it, and shopifyVariantId once a sync has linked it. active: false = discontinued.
bundles[]Each has id, sku, name, items:[{productId, qty}], storedPrice, plus optional giftIncluded, skipped, note, history, shopifyVariantId. active: false = discontinued.
trash[]{kind: "product"|"bundle", item, at} — deleted items, restorable until permanently removed.
excludedSkus[]Normalised SKUs of products you've deliberately deleted. Never re-added by a sync.
excludedBundleNames[]Normalised names of bundles (or no-SKU products) you've deliberately deleted. Never re-added as a bundle shell.
lastSyncAtTimestamp of the last one-click sync — drives the 4h cooldown.

Reorder — data/reorder.json or Redis bundle-manager:reorder

FieldWhat it is
items{zohoId}From Zoho: name, sku, vendor, unit, reorderLevel, stockOnHand, toReceive, openPOs; flags below, missing; typed here: expectedDate, notes.
manual{SKU}Ceramitec bundles' typed fields: toReceive, expectedDate, notes. A Zoho refresh never touches these.
lastSyncAtLast refresh of any kind.
lastManualSyncAtLast Refresh-button press — drives the 8h cooldown.

Bundles are matched to Shopify by name (they have no reliable SKU); products are matched by SKU. That asymmetry is why the exclusion list has two separate arrays, and why two bundles sharing a name is flagged as ambiguous (more below) while two products sharing a name isn't.

The three Shopify sync operations

Three scripts do this independently (each dry-run by default, --apply to write); the in-app button runs all three in one pass — one Shopify fetch, one write.

New products
Active Shopify variant, has a SKU, not already in the catalog by SKU, not in excludedSkus → added as a product. A product without a SKU is matched by normalised name instead, and only added with --include-nosku. scripts/sync-store.js · lib/shopifySync.js
New bundle shells
Active Shopify listing, no SKU, name not already a bundle or product, not a gift-card/voucher/test-item keyword, not in excludedBundleNames → added as an empty bundle (name + price, zero components) — this store's convention is that a combo/packaged listing has no SKU while a real standalone product does. scripts/import-bundle-shells.js · lib/shopifySync.js
Stock refresh
Every product matched by SKU gets stock/stockTracked updated from Shopify's inventory_quantity. Never adds or removes anything — nothing to update for a deleted product, so deletions are already safe here without any exclusion list. scripts/fetch-stock.js · lib/shopifySync.js

None of this ever edits an existing product/bundle's price, items, or history — only adds new records and refreshes the stock fields.

The "Sync with Shopify" button

One header button, one Shopify fetch, all three operations above in a single write. Throttled to once every 4 hours, enforced by the server (POST /api/sync) via lastSyncAt — not just a disabled button, so it's safe even if the endpoint were hit directly. Deletions are remembered (the exclusion list)

Before this, deleting something didn't stop it coming back — a sync only checks the current live products/bundles, not trash, so a deleted item's SKU/name would look "new" again next time. Now:

On delete

deleteProduct / deleteBundle

A product with a SKU excludes that SKU. A bundle, or a no-SKU product, excludes its normalised name — because a no-SKU product would only ever come back as a re-detected bundle shell, same as a deleted bundle would.

On restore

Undo, or Restore from Trash

Clears the matching exclusion entry. Works whether it's still sitting in Trash or you click Undo right after deleting.

Permanent delete

Delete from Trash / Empty trash

No extra step needed — the exclusion was already added at the moment of the original (soft) delete, and permanent deletion doesn't remove it. This is deliberate: once deleted, always excluded, unless restored.

Known limitation

These two arrays only ever grow — nothing prunes them automatically. Fine for normal use; worth knowing if you ever do a huge cleanup pass.

A quiet bug this fix exposed — later got much bigger

The autosave PUT used to replace the whole stored document with just {products, bundles, trash} — so lastSyncAt (and these exclusion lists) would've been silently wiped on the very next edit after any sync. First fix: merge onto the previous document instead of replacing it. Then a colleague's "Gift / packaging price included" checkbox got silently reverted on a real bundle — traced to the same root cause at a larger scale: two people with the app open at once, whoever autosaved second would overwrite the other's edit to any item, not just the one they were touching, because the save still sent (and the server still replaced with) the entire array. Real fix: lib/mergeData.js — the client now diffs against its last confirmed-saved state and sends only what changed (by id); the server reads fresh and merges just those items in, then returns the full merged doc so the client also picks up anyone else's concurrent edits. The push-price endpoint had the same bug in miniature — read once, wait through a slow Shopify round-trip, write the whole array back — fixed with the same read-fresh-then-merge discipline.

Stock & the Out of stock tab

A product only counts as out of stock when it's active and tracked and at zero — an inactive/discontinued item is already flagged separately as "missing," never double-counted as an OOS blocker.

The tab

  • Ceramic / Marble tabs at the top split everything in two. Marble is anything with "marble" or "vase" in the name, the Claude / Horizon / Arc / Pivot Marble lines, and Buoy coasters and Aura trivets; Ceramic is the rest. A tab with nothing in it is hidden. This is a wider rule than the Products tab's "Marble Atelier" filter, which is just the four named lines.
  • Bundles blocked by an out-of-stock component (open by default, A–Z) — each bundle with the component(s) holding it up. Click one to edit it in place.
  • Single products at zero stock (collapsed by default) — every other zero-stock product. A product already named against a bundle above isn't listed again here. Click one to jump to it on Products.
  • Empty sections are hidden rather than shown as "0".

Word download

The button on the right — Download OOS Ceramic or Download OOS Marble, matching the tab you're on — first refreshes the data, then saves out-of-stock-ceramic-YYYY-MM-DD.docx (or -marble-). The file has a title, the date and counts, and a two-column table: Name and Out of stock. Bundles come first with their out-of-stock components in the second column; single products follow with that column blank. Same de-duplication as the screen.

How fresh is "refresh"?

If the 4h sync cooldown has passed, the download runs a full Shopify sync first. Otherwise it reloads what the server has, which the 4-hourly stock Action keeps current — so at worst the stock is about 4 hours old.

Elsewhere

  • Bundle's own sellable stock — for each active, tracked component, stock ÷ qty needed (rounded down), then the least of those. Shown on the Bundles row and in the editor.
  • "Out of stock" filter pill on both Bundles and Products — both tabs open on it.
  • Stock column on Products — — means Shopify isn't tracking inventory for that item, so it's never treated as out of stock.
  • The count on the main nav's "Out of stock" label is bundles only, both lines together.

Zoho Inventory

Separate from everything Shopify. Lists every active, stock-tracked Zoho item whose stock on hand is below its reorder level — the same list as Zoho's Vendor → Order Now screen, plus dates and notes Zoho doesn't have.

  • Vendor filter — Hollyhock is pre-selected; the vendor column hides when one vendor is picked.
  • Refresh never deletes a row and never touches dates/notes. Items back above their reorder level move to Restocked; items Zoho stops returning are kept and flagged.

  • /inventory — a page with only this table, for sharing with the team. It's behind the same site login, so it hides the rest of the app but doesn't lock anyone out of it.

Smaller behaviours worth knowing

Duplicate bundle names

dup name

Since bundles are matched by name, two bundles with the exact same (normalised) name are genuinely ambiguous — which one does a Shopify listing, or a future sync, actually mean? Flagged with an amber "dup name" badge and a "Duplicate names" filter pill on the Bundles tab.

Computed vs. live bundle price

display

Bundle rows show the computed sum of their items — except when "Gift / packaging price included" is checked, where the mismatch is deliberate, so it shows the live Shopify price instead rather than making it look broken.

Confirm dialogs

permanent only

A styled in-app modal, only for actions you can't take back: deleting from Trash, emptying Trash, and pushing a price to Shopify. Ordinary deletes go to Trash with an Undo toast instead.

Search

token match

Every word you type must appear somewhere in the name/SKU, any order, partial words OK — "lun pla" finds "Lunar Nude Plate". The "Search everything" box (products and bundles at once) is built but hidden for now.

What shipping each feature actually required

None of these were "just add the feature" — each one surfaced a real edge case once it touched actual data.

Push price to Shopify

first live-store write

Everything before this only ever read Shopify or wrote to this app's own data. A price push had to target an exact Shopify variant, not a name/handle looked up at push-time — because we'd already found real Shopify-side duplicates (a draft + an active listing, same name, different prices). So every product/bundle gets its shopifyVariantId captured during any sync (backfilled once against the whole catalog), and a push only ever fires against an id already on file. Confirmed first, since nothing else here writes to the live store.

Marble Atelier / marble-vase-Lush-Diverge silos

keyword matching

Naive substring matching on "lush" would false-positive on "Blush" — needed whole-word matching instead. Bigger issue: once bundles/products were split into a separate "silo" hidden from the default filters, the jump-to-product / jump-to-bundle navigation could land on an item that's invisible under whatever filter is currently selected — hit this twice, both fixed by checking which silo the target actually lives in before navigating.

Duplicate bundle name flag

found a real one

Building the check surfaced an actual duplicate live in the catalog — two bundles both named "Chaat Table Setting (7 Pieces)", same 5 items, same price. The deeper cause turned out to be the exclusion-list gap: a deleted bundle silently resurrected by a sync, then rebuilt by hand. Only empty (never-rebuilt) resurrections are safe to clean up automatically; anything with real component work in it needs a human call.

Sellable stock (qty-aware)

wrong the first time

First version took the raw minimum stock across a bundle's components. Wrong the moment any component needs more than one per bundle — a part needed 9-per-bundle sitting at 58 units supports 6 complete bundles, not 58. Fixed to divide by qty first, floor it, then take the minimum.

Bundle ↔ Product jump navigation

round trip

Jumping back to a bundle lands on Needs updating if it's actually stale there (where you'd act on it), otherwise the plain Bundles tab — with the same silo-awareness as above in both directions.

Sticky filter bars

layout

The header and each tab's filter row both stick, stacked. The second one's offset is measured live (getBoundingClientRect()) rather than hard-coded, so a longer nav label can't break it.

Sort by name / price / stock

null handling

Items with untracked stock have no number to sort by. Sorting them as zero would cluster them with genuinely-out-of-stock items — so they always sink to the bottom, whichever direction.

Zoho "to be received"

not in the API

Zoho's item API doesn't expose the number its own Order Now screen shows. It's rebuilt from open purchase orders, ignoring closed ones, using the larger of received and billed so a PO billed before it's received isn't counted twice. Calls are rate-limited and access tokens reused, since Zoho caps both.

Out of stock: Ceramic / Marble + download

Oct 2026

Listing every zero-stock product under the bundles doubled up — most were already named as a bundle's blocker. Those are now left out of the product list, on screen and in the Word file. The download refreshes before building, and works within the shared 4h sync cooldown rather than getting around it.

Worth knowing, not a bug

A Shopify-side duplicate — two listings with the identical name, one draft with the correct price, one active at ₹0 — will sync in whichever is active, ₹0 included. Verified directly against the Shopify API: the code was correctly reading exactly what Shopify returned. That's a data-hygiene issue on the Shopify side (archive/fix the stray duplicate there), not something the sync logic should second-guess.
